# 实速原画提交与帧节奏审视

有效原始记录：[runtime-frame-performance.json](runtime-frame-performance.json)，独立run `2026-10-22T22-58-35-730Z`。8个代表窗口完成，状态为 `observed`，不是全设备流畅度认证。没有修改产品、程序场、原材质、相机或作者时钟；没有因为录像约21fps而修改源渲染。

## 环境与方法

Windows，headless Chrome156.0.8078.47；实际GPU读取为 ANGLE / NVIDIA GeForce RTX5070Ti / D3D11。其他任务和root产品GPU页面已关闭，root未同时录片/编码。每个新上下文先正常入卷，seek到代表位置，等待当前可见资源就绪及1200ms稳定，再通过实际自动展卷按钮启动。没有网络/CPU限速、清除OS/驱动缓存或强制GC；测量窗口内没有截图/录屏，结束后才各保存一张截图。

依次测1920×1080 CSS / DPR1及2560×1440 CSS / DPR1.25，每卷一个至少20秒窗口，起点分别为0.76、0.30、0.40、0.32。第一卷窗口覆盖后段原生光晕，第四卷覆盖宫廷向离散的转折；不是全卷遍历。按既定顺序串行，未随机化，因此两种配置的差异不能当成分辨率引起的因果收益。

页面rAF用独立轻量回调收集原生时间戳。原画提交使用canvas累计 `renderCount`，该计数仅在原画渲染路径完成CPU提交后增加；DOM诊断名义约100ms更新，因此只在新计数属性观察边界取20秒累计差，**不把诊断属性间隔当成逐原画帧间隔**。报告保留所有观察及间隙，并给出窗口时长偏差±200ms的速率敏感范围；任意长任务的调度误差不能靠一个固定边界保证排除。

这些是回调/CPU提交路径的吞吐，不是GPU完成计时，更不是显示器真正呈现帧。没有 `gl.finish`、GPU计时query、私有React访问、原函数hook、加速或替换时钟。CDP Performance指标仅在端点读取；其累计范围比帧窗口稍宽，不能把各项时间当成同一精确20秒内的函数自耗时。

## 实际结果

单位：提交与rAF为每秒；最大间隙为页面rAF毫秒。

| 卷 | 1920 rAF / 原画提交 | 2560 DPR1.25 rAF / 原画提交 | 1920最大间隙 | 2560最大间隙 |
|---|---:|---:|---:|---:|
| 一 | 115.09 / 110.26 | 109.46 / 105.24 | 394.4 | 138.8 |
| 二 | 167.56 / 166.62 | 178.35 / 177.40 | 138.8 | 27.8 |
| 三 | 128.48 / 127.84 | 170.53 / 168.04 | 677.8 | 72.2 |
| 四 | 166.04 / 164.76 | 177.50 / 176.35 | 111.1 | 38.9 |

平均吞吐较高，**不能掩盖首访长停顿**：1920第三卷记录24次longtask，最大680ms；第一卷8次，最大392ms。后测2560第三卷为2次、最大75ms，第一卷4次、最大134ms。窗口内仍有后续资源流入；可能涉及首次纹理上传或材质变体准备，但本轮没有函数级profile，不能直接归因给图像decode、shader compile、阴影、React或布局。下一步如需处理，应对首访第三卷独立profile，而不是仅凭平均数宣称没有抖动。

各窗作者时钟进度误差均小于0.0001，相当于至多约9.5ms源时间；低提交频率没有被用来放慢电影。20秒窗口的累计Layout约0.118–0.179秒、RecalcStyle约0.757–1.032秒，只能说明总体布局量级，不能归因到具体组件。

CDP端点 `JSHeapUsedSize` 为约12.97–37.82MiB；页内 `performance.memory` 的峰值估计最高244.86MiB，两者口径和采样不同，不把差值解释为泄漏，也不当成VRAM或进程RSS。没有强制GC，因此不是保留内存证明。`textureBytes` 峰值第一卷263.71MiB、其他卷约157–159MiB；这是源纹理预算估算，当前必须可见的纹理不能为满足160MiB软回收线而被剔除。

原画canvas实际buffer及CSS门均在每个case记录。由当前 `sourceTargetSize` 公式、实际sourceViewport及DPR派生的后处理目标：前三卷两配置均为2730×1536，第四卷为2380×1700及2423×1730；均在4096边长和4Mi像素上限内。这些目标尺寸是有来源的计算，未越过私有对象读实际render target。HDR/深度/阴影内存没有做VRAM总量实测。

## 代码审视：成本与保真边界

- `SourcePostProcessing.render` 按实际视锥内DITHERED张数N做深度分层，包含3N+3次render调用，启用DOF再多1次。这里有fullscreen合成，不能把全部调用都说成整场景绘制；`SourceMaterialLibrary.setPass` 已经用 `material.visible` 区分DITHERED/BLENDED。全卷程序总张数为28/4/3/1，不等于每帧视锥内N。Film有36次纹理采样，DOF仅在条件成立的像素做32环采样；不能为了帧数删掉源效果或任意减少层数。
- 阴影每帧重绘：第三卷3个AREA灯，其余各1个有效阴影灯，目标均2048²。`fitLampShadow` 同时依赖当前view camera、focus与视锥；camera-only改变也会改变阴影投影/覆盖与采样。仅以mesh matrix未变缓存会漏掉显隐、morph、UV/程序mask/alpha、字段贴图、灯和实际阴影相机变化。
- 若以后确需保真缓存，安全key至少包括实际阴影投影矩阵、caster深度状态及所有影响alpha/mask的源程序输入/贴图版本、可见性、形态键、灯状态。保守包含全部相关材质uniform更可靠，但移动镜头时预期命中有限；不能宣称这种缓存必然解决680ms首访长任务。
- 当前source版不执行 `calligraphy.load`，旧CSS3D题字场景为空，不能把旧复杂布局当作当前热点。实际短章DOM每卷15/12/9/9条，45是四卷合计。静态协审没有发现每帧显式layout读取往返：尺寸来自ResizeObserver，稳定播放的layout effect主要写ref；cue/resize/大seek时才重新锁位。重建JSX和React遍历是候选成本，尚未证明是帧瓶颈。
- 非侵入候选只保留为研究：复用同帧world bounds/源轨取样、避免不可见材质pass中的冗余状态更新、在真实函数证据指向首次程序准备后评估 `compileAsync`/上传调度。它们仍须证明输出和失败恢复完全相同，再重跑原生严格保真与完整生命周期。当前不实施。
