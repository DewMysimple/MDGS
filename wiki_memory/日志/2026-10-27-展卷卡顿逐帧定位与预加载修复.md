# 展卷卡顿逐帧定位与预加载修复

## 目标与证据

用户反馈30/60帧自动展卷有卡顿，要求逐帧检查录屏并优化，保留设计和源场景，结果仅留本地。任务起点main `0ed4897`，工作树干净。逐帧检查提供的460帧、30fps、约15.33秒录屏：首卷约53%—64%播放时出现连续约100毫秒画面几乎不变，约13秒后为手动暂停；录屏未显示画质帧率选项，不能仅凭它确定具体档位或区分录屏和应用卡顿。

通过本机独立配置回放、记录画卷源帧提交和资源加载发现：播放控制与渲染各有时钟，产生节拍错位；扩张预加载视锥误把未来资源计入当前帧门控；未来需要的纹理和数值场在进入画面或阴影时才开始请求；部分离屏缓冲反复分配。进一步定位同图31个采样器逐帧初始化占满预加载槽，导致山景纹理排队至画面需要时。

## 实现

统一控制器和画卷绘制的节拍，保留资源未就绪时暂停时钟及每次最多推进一个源帧。真实视锥与阴影投射者决定当前帧资源门控；邻近和沿运镜方向1/2秒预测的资源提前预热，1秒内优先，并限制预测候选和并发，保留当前帧优先。预测64 MiB为估算软预算，并非总显存上限；原有近景、后处理预加载不包含其中。相同 source 和 Three r180 GPU cache key 的采样器每帧最多32个一起注册，不同 GPU 状态仍分帧，全部准备完才解锁。复用临时不使用的离屏缓冲，实际尺寸或画质变化时释放。没有修改原Blender、原图、源运镜或入场轨。

## 验证与局限

- `npm run test:scene-stability`：显隐4、播放时钟14、阴影10、渲染18项通过；`npm run test:scroll-input` 22项及 `npm run test:peony2-clock` 通过。检查包含250Hz显示节拍、资源等待、相同/不同采样器、反向预取、切卷及上下文恢复的模拟或静态逻辑。
- 本机Windows、i5-14600KF、RTX 5060 Ti、2560×1440/250Hz。隔离配置启动打包Electron、720p、首卷53%起约12秒：30帧档大于80ms的画卷源帧提交间隔9→0次，资源等待1167.5→0ms；60帧档6→0次，等待822.1→0ms。每档新旧各一次，统计画卷提交而非显示器呈现，不能推断所有设备和所有时段表现。诊断版观察到山景纹理由到帧1956才请求改为帧1933加载并在1934驻留。
- 较早候选版本四卷各从53%起，720p的30/60各6秒共八次，均无超过80ms间隔；同候选首卷2K/30、2K/60各12秒均无超过80ms间隔。这些不是最终版完整四卷/全部档位验收。
- 最终打包Electron运行 `scripts/validate-desktop.mjs`：12项通过，覆盖四卷离线画面及交互、全屏、原文、花笺下载和资源完整性；打包检查原图原字节、ZIP CRC与解压哈希。没有在学校低配机或跨GPU实测，亦未逐帧播放全四卷；性能仍取决于设备和画面。
